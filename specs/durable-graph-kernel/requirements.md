# EG-DURABLE-KERNEL requirements

| ID | Requirement | Verification |
|---|---|---|
| `EG-DURABLE-KERNEL-R001` | **Outbox head-only attempt accounting and rewind.** The outbox increments retry attempts only for the row currently at the head of a stream, so a failing head cannot exhaust the attempt budget of healthy successor rows. Consumers can declare an explicit reject that dead-letters the head immediately and reports the transition, and an administrator can list head status and dead letters and issue a rewind to replay from an earlier position. | Verified by outbox tests covering a failing head never dead-lettering a healthy successor, repeated head releases dead-lettering only the head, consumer reject dead-lettering immediately, and rewind replay. |
| `EG-DURABLE-KERNEL-R002` | **Outbox consumers get per-class topics and reject-driven rebuild.** Outbox consumers publish to semantically distinct topics per message class, and a reasoning-projection consumer that rejects a message triggers a rebuild rather than silently acknowledging a skipped projection. `MutationOutbox` exposes an administrative method for inspecting and managing consumer state, and the outbox reports metrics on attempts, rejects, dead letters, and rebuilds. | Verified by outbox integration tests asserting per-class topic routing, reject-triggered rebuild of a reasoning projection, and exported outbox metrics. |
| `EG-DURABLE-KERNEL-R003` | **Owner-store layout lineage registry with typed upgrade refusal.** The owner-store layout maintains a lineage registry that recognizes every supported on-disk format and refuses an unsupported layout with a named `{LAYOUT}_FORMAT_UPGRADE_REQUIRED` error rather than reinterpreting it silently. A generated document records the steps required to remove a retired layout from the registry. | Verified by a golden lineage test that loads each supported manifest format and checks the typed refusal for unsupported ones. |
| `EG-DURABLE-KERNEL-R004` | **Outbox attempt accounting is scoped to the head row.** Re-leasing an outbox row increments the attempt count only for the row currently at the head of its stream, never for healthy successor rows staged behind it, so a failing head cannot cause successors to be dead-lettered alongside it. This accounting is implemented in `crates/eg-transaction/src/outbox/claim.rs`. | Verified by a test asserting a failing head never dead-letters a healthy successor, and a test asserting sixteen re-leases of the head dead-letter only the head. |
| `EG-DURABLE-KERNEL-R005` | **Outbox delivery state remains local to the owning node.** Outbox delivery-side rows are written by the local store owner and are not replicated by the multi-group raft layer, so delivery progress is node-local rather than part of the replicated log. | Confirmed by an integration test checking that outbox delivery rows are not present in replicated state on non-owning cluster members. |
| `EG-DURABLE-KERNEL-R006` | **Engine startup does not block on one store's lazy open.** Engine startup must not refuse entirely when the agent-library store fails to open; that store opens lazily so a failure to open it affects only operations that depend on it, not overall startup. | Verified by a startup test that forces the agent-library store to fail opening and asserts the engine still starts and serves unrelated functionality. |
| `EG-DURABLE-KERNEL-R007` | **Host binary exposes a storage inspect and upgrade command.** The host binary provides an administrative `storage inspect` and `storage upgrade` command surface for examining and migrating on-disk layout state outside of normal server startup. | Verified by a CLI integration test exercising `storage inspect` and `storage upgrade` against a sample data directory. |
| `EG-DURABLE-KERNEL-R008` | **Raft unit tests pass under cluster features and run in CI.** All `raft::*` unit tests and `txn_reconcile_ack_lost_retry` pass when compiled with cluster features enabled, without recursion-depth failures, and a continuous-integration job compiles and runs the raft test suite on every change. | Verified by a green continuous-integration job that builds with cluster features and executes the raft test suite, including `txn_reconcile_ack_lost_retry`. |
| `EG-DURABLE-KERNEL-R009` | **Native raft commands are sealed as their bare method.** Native consensus commands are sealed and opened as the bare method they represent in `src/raft/command/native/sealed.rs` (`SealedNativeMethod::seal_value`/`open_value`), so a native raft command payload is never rejected as invalid due to a mismatched envelope. | Verified by a follower catch-up test that replays a create-graph-then-write sequence and by unit tests on `SealedNativeMethod` sealing and opening. |
| `EG-DURABLE-KERNEL-R010` | **jscpd clone gate runs on every commit.** The jscpd structural-clone gate runs as part of the per-commit check suite, so a complexity-reducing extraction cannot silently introduce a new duplicate code pair without being flagged. | Verified by confirming the per-commit hook configuration invokes the jscpd gate and that a deliberately duplicated extraction is caught by it. |
| `EG-DURABLE-KERNEL-R011` | **Clippy and targeted tests cover the full and all-features builds.** Continuous integration compiles and runs clippy against the full feature set without raft, and against all features with the Kafka client libraries present, and runs the targeted raft, backup, and persistence test modules before any change is accepted. | Verified by continuous-integration logs showing a passing full-feature clippy run, a passing all-features clippy run with Kafka dependencies enabled, and passing runs of the targeted raft/backup/persistence test modules. |
| `EG-DURABLE-KERNEL-R012` | **Raft native command sealing and placement routing are correct.** Native consensus commands are sealed and opened consistently so they are never rejected as invalid, and placement administration correctly routes data movement across a multi-node raft cluster. | Verified by a follower catch-up replay test and a placement-admin test that moves data across a real three-node cluster. |
| `EG-DURABLE-KERNEL-R013` | **Raft cluster test failures capture a causal trace automatically.** A failing multi-node raft test automatically captures a bounded ring-buffer trace of raft and heartbeat events, filtered to the consensus-related targets, and dumps it through a panic hook, implemented in `src/raft/harness/trace_capture.rs`, so a failure's causal chain is available without manually enabling tracing. | Verified by unit tests on the ring buffer, including eviction of the oldest entry when over capacity, plus the panic-hook dump path. |
| `EG-DURABLE-KERNEL-R014` | **Raft cluster tests pass reliably under load.** The leader-rebalance and the three-node placement-admin cluster tests reach the correct cluster end state and pass reliably under representative load, not only on an idle host; timing or ordering gaps related to the transport issue in EG-DURABLE-KERNEL-R015 do not cause spurious test failures. | Verified by repeated runs of both tests under representative CPU load with no flaky failures, backed by causal trace capture on any failure. |
| `EG-DURABLE-KERNEL-R015` | **Raft heartbeat flush and batch dispatch avoid head-of-line blocking.** Heartbeat flushing is independent per peer rather than shared across one coalesced batch, and per-group batch dispatch proceeds concurrently rather than blocking behind a single in-flight write for its full commit duration, so one slow peer or group cannot stall heartbeat or write processing for the others. | Verified by a benchmark measuring worst-case heartbeat processing time under load, with any remaining head-of-line risk bounded by a documented single-graph-per-group configuration. |
| `EG-DURABLE-KERNEL-R016` | **Raft durability writes are batched to reduce commit latency.** Raft log append and commit batches multiple entries using durability batching and coalescing rather than issuing one redb write transaction per entry, reducing commit latency that otherwise runs on the order of a second per transaction regardless of cross-group contention. | Verified by a focused raft durability test and by commit-latency measurements comparing per-entry commits against batched commits. |
| `EG-DURABLE-KERNEL-R017` | **Correctness-gated benchmark compares EG against HelixDB.** A pinned, correctness-gated benchmark suite measures point-get, multi-hop traversal, transactional batch, text/vector prefilter, and mixed graph/vector workloads against HelixDB, reporting latency, throughput, CPU, resident memory, and storage amplification for each. | Verified by a benchmark report that records exact configuration, hardware class, code revision, and measured results, with no superiority claim accepted without it. |
| `EG-DURABLE-KERNEL-R018` | **UDF registry and response-dedup cache are tenant-scoped.** The UDF registry is keyed and scoped by tenant and actor through a single authorization chokepoint, so a UDF registered by one tenant cannot be invoked or shadowed by another tenant, consistent with the foreign-source scoping in EG-FEDERATED-QUERY-R013. The in-memory mutation response-dedup cache keys its entries by tenant and caller so one tenant's cached response is never replayed to another. | Verified by cross-tenant negative tests asserting UDF invoke and shadow attempts are denied, and that the response-dedup cache does not replay another tenant's cached response. |
| `EG-DURABLE-KERNEL-R019` | **Graph lifecycle idempotency keys are tenant-scoped.** The lifecycle batch identifier used for `CreateGraph` and `DeleteGraph` idempotency includes tenant in addition to the verified agent identity and graph name, so two tenants using the same agent identity, idempotency key, and graph name never receive each other's replayed result or reveal cross-tenant graph existence. | Verified by a test creating the same idempotency key, agent identity, and graph name under two different tenants and asserting each gets its own independent outcome. |
| `EG-DURABLE-KERNEL-R020` | **Bounded background scrub detects node corruption between restarts.** A background content scrub reads nodes using a read transaction with no write lock, resumes from a stored key cursor, runs at a bounded rate, and surfaces typed corruption findings on status and metrics, rather than relying on detection only at read time or the next restart. Unseal failures return a typed error instead of an untyped string. | Verified by a test that corrupts a persisted node, runs the scrub, and asserts a typed finding is reported and the cursor resumes correctly after restart. |
| `EG-DURABLE-KERNEL-R021` | **Store-authority binding validates once per write transaction.** `binding_for_write` in `crates/eg-storage/src/physical/binding.rs` validates owner-store authority and scope once per write transaction and caches the result for that transaction's duration, rather than repeating the full manifest and table check on every member access, while still failing closed at the transaction boundary. | Verified by a commit-latency benchmark showing per-commit validation overhead drop to a small constant cost instead of repeating per-member checks. |
| `EG-DURABLE-KERNEL-R022` | **Just-in-time RBAC elevation requires two-person approval.** A dedicated `rbac.elevation` control lease is consulted by the access-check path to grant temporary elevated access, requires approval from two distinct principals, carries a hard expiry, is audited, and is never issued automatically by a learning or inference process. | Verified by tests asserting elevation is denied without two distinct approvers, denied after expiry, and always produces an audit record. |
| `EG-DURABLE-KERNEL-R023` | **UQL enforces a read-only guarantee at compile time and by test.** `UnifiedQuery`, `UnifiedQueryText`, and `Uql` operations never perform a mutation or touch a durable domain, are idempotent, and execute against a `Snapshot`; a compile-time pin ensures operation dispatch takes the snapshot by shared reference so a mutable path cannot be introduced without a build failure. | Verified by an eg-capabilities invariant test asserting the read-only, idempotent, snapshot-based contract for all three query types. |
